# RunningHub 本地 Codex 生图节点

使用已登录的 Codex 内置生图工具，在原 RunningHub 图片节点保存结果与历史。比例作为画面要求传给工具；分辨率、质量、模型版本由原生通道管理。

## 维护

源码目录：`server/local-gpt-image/`。安装位置可自选，完整步骤见 [Chrome 与 MCP 配置方案](../../docs/CODEX_IMAGE_SETUP.md)。

服务维护应运行仓库中的 `node scripts/rh-image-safe-restart.mjs`。该脚本先取得维护许可，运行中、回填中或等待续作的图片会阻止许可；维护期间新请求被拒绝。不要绕过检查直接重启正在生图的服务。修改文件后需要更新服务时，同样先取得维护许可，再安装与重启；失败的许可不是继续执行的授权。

## 结果与重试

- 每个批次始终使用同一个节点和批次 ID，已完成的索引不会重新生成。
- 只有明确失败且没有任何图片回传的普通 HTTP 429，才会自动续作。默认最多两次，逐次延长等待；`autoRetryLimit: 0` 允许严格只提交一次。
- Cloudflare / HTML 安全验证、用量耗尽、未知网络结果和上传不确定性不自动重发。网页验证通过也不能保证原生生图通道立即恢复。
- 本地服务意外结束的请求标记为中断并持久化。上游是否完成未知时，保留请求、图片与回执，不能默认为失败而重新生成。

## 延迟控制

默认全局同时处理 4 张图片。点击任一 Codex 节点，在“并行数量 · 全局”选择 1–4 张，所有节点与画布共用此设置，自动保存至 `~/.runninghub-canvas-bridge/gpt-images/settings.json`，刷新页面与重启服务后保留。调高会立即启动等待任务；调低不取消已发出的任务，后续按新的上限启动。保存失败时保留原上限；已保存文件损坏时暂按 1 张运行并提示重新选择。

不再使用全局单任务锁或固定 60 秒的提交间隔。不同节点可同时提交；一个节点的 2–4 张也按单张任务使用同一并行池。超过所选名额的任务显示排队，名额释放后在不同批次间轮转。普通 HTTP 429 才触发全局退避，修改并行数量不会绕过退避，已在生成的其他图片继续完成。

每张图片使用独立的原生线程、输出索引及回执。同一节点的回填按顺序提交，避免历史记录互相覆盖。节点内部仍只允许一个活动批次；参数、参考图和结果选择只锁定正在处理的节点。取消只作用于本批；已发出的上传会保存回执。服务重启后不自动重放未确认的请求。

图片工具返回有效字节后立即落盘、回填原节点，并结束不再需要的模型收尾。画布连接按精确画布缓存，收起的编辑面板暂停详细轮询，节点仍由轻量任务轮询显示状态。并行是本机调度能力，上游仍可能因用量或安全验证拒绝请求。

测试：`node --test server/local-gpt-image/integration.test.mjs server/local-gpt-image/nodes.test.mjs server/local-gpt-image/parallel.test.mjs tests/runtime.test.mjs`。真实图片成功、上传回读与网页视觉检查仍需分别验证。
